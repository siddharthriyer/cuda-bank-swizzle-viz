Bank conflicts and XOR swizzle to deal with them

Shared memory is 32 banks wide. A warp's 32 lanes are happy only when they hit 32 different banks. If you store tiles row-major, a column read will pile all 32 lanes onto one bank and it will cause a 32× stall. WGMMA and TMA rely on a single XOR to fix this. This visualization allows you to toggle the XOR and then hover any cell to see how the bank gets computed.

Reading the bit inspector

Every cell lives at word index row·32 + physCol, and because the row stride is exactly 32, the low 5 bits of that index are the bank. Under no swizzle the physical column is just the logical col, so bank = col — a column read overloads one bank. Under the XOR swizzle the physical column is col ⊕ row, so each lane's row "spins" its bank to a different value, and the 32 lanes become scattered across all 32 banks. The inspector shows exactly those 5 bits being XORed.

Why WGMMA needs this

Hopper's wgmma.mma_async feeds the tensor cores straight from shared memory, reading operand tiles in transposed / column-strided patterns. With naive row-major layout these accesses are serialized and take unnecessary time. So the operand's 64-bit matrix descriptor carries a swizzle-mode field (none / 32B / 64B / 128B) telling the MMA unit the data is stored sheared and to address it that way. The matching TMA copy (cp.async.bulk.tensor) applies the same mode moving the tile global→shared, so it lands pre-sheared. This makes it conflict-free for ldmatrix and the tensor core alike with no extra passes and no extra storage required.

Real atoms (128B/64B/32B) XOR only a few bits at a vector granularity — a partial version of the full ⊕ shown here — but the mechanism is identical.
